## 0. The finding that reshapes the whole plan

While reading the real `ury_order.json` schema, one thing became clear that neither v1 nor any of the six reviews stated explicitly:

**`URY Order` is not the order record. It is a Frappe UI form.**

Its fields are `table_tab`, `menu_tab`, `item_search`, `all_item` (Button), `cart_items` (HTML), `favorite_items` (HTML), `table_list` (HTML) — screen furniture. It has **no status field**, **no docstatus workflow of its own**, no tax fields, no payment fields, and no invoice numbering. What it does have is `last_invoice → POS Invoice` and a `grand_total` mirror.

The actual order of record is **ERPNext's POS Invoice**. `ury_order.py` is a controller that drives POS Invoice documents, and `URY Order` is the single-doctype scratchpad the cashier screen binds to.

Three consequences:

1. **v1's `Order` struct was fiction twice over** — not just wrong fields, but the wrong entity. There is no `OrderStatus` enum to port because there is no status column. Order state lives on POS Invoice (`docstatus`, `status` ∈ Draft/Paid/Consolidated/Return, `consolidated_invoice`).

2. **A Rust rewrite is not "port 36 doctypes."** It is "reimplement ERPNext's POS Invoice, Sales Invoice, Stock Ledger, GL Entry, and tax engine, then port 36 doctypes of restaurant-specific logic on top." The 36 doctypes are the small half.

3. **The migration boundary is not where v1 drew it.** Of the 36 URY doctypes, 24 are child tables and only 12 are root entities. The load-bearing entities are ERPNext's.

Everything below is written with that correction in place.

**`merged_with` is a `Data` field holding CSV**, and it lives on `URY Table`, not on the order. v1 read it off the order and would have merged the wrong things. Model it as a newtype that owns the parsing so the CSV format never leaks:

```rust
#[derive(Debug, Clone, Default)]
pub struct MergedWith(Vec<TableName>);

impl MergedWith {
    /// Mirrors _parse_merged_with in ury_order.py. Tolerates empty strings,
    /// stray whitespace, and trailing commas, because production data has all three.
    pub fn parse(raw: Option<&str>) -> Self {
        MergedWith(
            raw.unwrap_or_default()
                .split(',')
                .map(str::trim)
                .filter(|s| !s.is_empty())
                .map(|s| TableName(s.to_owned()))
                .collect(),
        )
    }
}
```

In Postgres this becomes a proper join table (`table_merges(table_id, merged_table_id)`) with a symmetric-pair constraint. Keep the CSV column during migration for reconciliation, then drop it.

Two data-quality landmines the migration must handle, both verified in the JSON:

- **`ury_kot_items.quantity` and `cancelled_qty` are `Data` (text), not numeric.** Any value that was ever written non-numerically will fail a `Decimal` parse. The migration needs a validation pass that reports unparseable rows rather than silently coercing them to zero.

| Frappe | Postgres | Note |
|---|---|---|
| `docstatus` 0/1/2 | `docstatus` enum | Draft / Submitted / Cancelled |

| Child table `parent`/`parentfield`/`parenttype`/`idx` | FK to parent + `idx INTEGER NOT NULL` | 24 of 36 doctypes are child tables |

### 2.5 The ERPNext boundary

Everything on the right is ERPNext, extended by URY via `hooks.py` fixtures. A Rust rewrite must either reimplement it or keep talking to it.

## 3. Business logic, ported correctly

### 3.1 Table merge — real signature and all guard rules

Real signature is `_get_merge_cluster(table)` returning `(members, table_by_name)`. It reads `merged_with` from **`URY Table`** rows and scopes the BFS to one `restaurant_room`. The wrapper `merge_tables_batch` enforces guards that v1 omitted entirely.

```rust
pub struct MergeCluster {
    pub members: HashSet<TableName>,
    pub by_name: HashMap<TableName, Table>,
}

/// Port of _get_merge_cluster. BFS is scoped to a single room —
/// tables in different rooms can never join a cluster.
pub async fn get_merge_cluster(
    seed: &TableName,
    room: &RoomName,
    repo: &TableRepo,
) -> Result<MergeCluster> {
    let room_tables = repo.list_by_room(room).await?;          // one query, not N
    let by_name: HashMap<_, _> =
        room_tables.into_iter().map(|t| (t.name.clone(), t)).collect();

    let mut members = HashSet::new();
    let mut queue = VecDeque::from([seed.clone()]);

    while let Some(current) = queue.pop_front() {
        if !members.insert(current.clone()) {
            continue;                                          // already visited
        }
        if let Some(table) = by_name.get(&current) {
            for neighbour in table.merged_with.iter() {
                if by_name.contains_key(neighbour) && !members.contains(neighbour) {
                    queue.push_back(neighbour.clone());         // room-scoped
                }
            }
        }
    }
    Ok(MergeCluster { members, by_name })
}

/// Port of merge_tables_batch. The guards ARE the business logic.
pub async fn merge_tables_batch(
    seed: &TableName,
    targets: &[TableName],
    repo: &TableRepo,
    orders: &OrderRepo,
    tx: &mut Transaction<'_, Postgres>,
) -> Result<MergeCluster> {
    let seed_table = repo.get(seed).await?;
    let cluster = get_merge_cluster(seed, &seed_table.restaurant_room, repo).await?;

    for target in targets {
        let t = repo.get(target).await?;

        // Guard 1: same room
        if t.restaurant_room != seed_table.restaurant_room {
            return Err(Error::CrossRoomMerge { seed: seed.clone(), target: target.clone() });
        }
        // Guard 2: not already merged into another cluster
        if !t.merged_with.is_empty() && !cluster.members.contains(target) {
            return Err(Error::AlreadyMerged(target.clone()));
        }
        // Guard 3: not occupied
        if t.occupied && !cluster.members.contains(target) {
            return Err(Error::TableOccupied(target.clone()));
        }
    }

    // Guard 4: refuse if the merged set would contain more than one live order
    if orders.count_separate_active(&cluster.members).await? > 1 {
        return Err(Error::MultipleActiveOrders);
    }

    // Row locks so two waiters cannot merge the same table concurrently — see §3.6
    repo.lock_for_update(tx, &cluster.members).await?;
    repo.write_symmetric_merges(tx, &cluster.members, targets).await?;
    Ok(cluster)
}
```

Changes vs upstream: room tables fetched once instead of per-hop (upstream re-queries), guards return typed errors instead of `frappe.throw` strings, and the write path takes explicit row locks.

### 3.2 KOT routing — 8 arguments, and the N+1 fixed

`process_items_for_kot` takes 8 arguments, resolves production units per `POS Profile.branch`, resolves `course` per item from `URY Menu Item` scoped by the room's menu, and flips `kot_type` to `"Order Modified"` when a submitted KOT already exists for that invoice + production unit. v1's 8-line grouping function modelled none of it.

```rust
pub struct KotRoutingRequest<'a> {
    pub invoice_id: &'a InvoiceName,
    pub customer: &'a CustomerName,
    pub restaurant_table: Option<&'a TableName>,
    pub kot_items: &'a [OrderLine],
    pub comments: Option<&'a str>,
    pub pos_profile_id: &'a PosProfileName,
    pub kot_naming_series: &'a str,
    pub room: &'a RoomName,
}

pub async fn process_items_for_kot(
    req: KotRoutingRequest<'_>,
    db: &PgPool,
) -> Result<Vec<Kot>> {
    let productions = list_production_units_for_branch(db, req.pos_profile_id).await?;

    // FIX for bugs 6 and 7: one batched lookup replaces
    // frappe.db.get_value("Item", ...) per item per station.
    let item_codes: Vec<_> = req.kot_items.iter().map(|i| i.item_code.clone()).collect();
    let item_group: HashMap<ItemCode, ItemGroupName> =
        fetch_item_groups(db, &item_codes).await?;
    let course_of: HashMap<ItemCode, MenuCourseName> =
        fetch_courses_for_menu(db, req.room, &item_codes).await?;

    let mut created = Vec::new();
    for production in productions {
        let groups = production_item_groups(db, &production.name).await?;

        // FIX for bug 1: the vector is built fresh per production unit.
        // ury_kot_validation.py:51 allocates it once outside the loop and appends
        // without reset, so station B's ticket carries station A's items.
        let station_items: Vec<KotItem> = req
            .kot_items
            .iter()
            .filter(|line| {
                item_group.get(&line.item_code).is_some_and(|g| groups.contains(g))
            })
            .map(|line| KotItem {
                item: line.item_code.clone(),
                item_name: line.item_name.clone(),
                quantity: line.qty,
                cancelled_qty: Decimal::ZERO,
                comments: line.comments.clone(),
                course: course_of.get(&line.item_code).cloned(),
                serve_priority: line.serve_priority,
                indicate_course: line.indicate_course,
            })
            .collect();

        if station_items.is_empty() {
            continue;
        }

        // Real upstream behaviour: an existing submitted KOT makes this a modification.
        let kot_type = if kot_exists(db, req.invoice_id, &production.name).await? {
            KotType::OrderModified
        } else {
            KotType::NewOrder
        };

        created.push(create_kot_doc(db, &req, &production.name, station_items, kot_type).await?);
    }
    Ok(created)
}
```

### 3.3 Menu resolution — three real strategies

`getRestaurantMenu` in `ury_pos/api.py` resolves room-wise (via the `menu_for_room` child table), order-type-wise (via `order_type_menu`), then falls back to the default active menu. Both mapping tables are child tables, which is why they do not appear as standalone entities.

### 3.4 COGS — two levels, `/ bom.quantity`, priced from `Item Price`

This is where v1 would have silently produced wrong numbers. Three behaviours must be preserved exactly:

1. **Exactly two levels** — `inner_bom_process` then `inner_inner_bom_process`, which stops. Not a depth-3 recursion.
2. **Divide by `bom.quantity`** (`ury_daily_p_and_l.py:38`) to normalise a batch BOM to per-unit cost.
3. **Price from `Item Price` on the configured `buying_price_list`** (`:30`) — *not* stock valuation, which is a different cost basis and will diverge.

Plus: upstream accumulates `unset_bom_items` so the operator can see which ingredients have no price. Dropping that turns a visible data gap into a silently understated COGS.

```rust
pub struct CogsResult {
    pub cost: Decimal,
    /// Ingredients with no Item Price. Surfaced, never silently zeroed.
    pub unset_bom_items: Vec<ItemCode>,
}

pub async fn cogs_for_item(
    item: &ItemCode,
    qty: Decimal,
    buying_price_list: &PriceListName,
    db: &PgPool,
) -> Result<CogsResult> {
    let mut out = CogsResult { cost: Decimal::ZERO, unset_bom_items: Vec::new() };
    explode(item, qty, buying_price_list, db, 0, &mut out).await?;
    Ok(out)
}

const MAX_LEVEL: u8 = 2;   // matches upstream exactly: two hardcoded levels

async fn explode(
    item: &ItemCode,
    qty: Decimal,
    price_list: &PriceListName,
    db: &PgPool,
    level: u8,
    out: &mut CogsResult,
) -> Result<()> {
    match find_bom(db, item).await? {
        Some(bom) if level < MAX_LEVEL => {
            if bom.quantity.is_zero() {
                return Err(Error::BomZeroQuantity(bom.name));   // upstream would divide by zero
            }
            for line in bom.items {
                // per-unit normalisation — omitting this scales COGS by the batch size
                let scaled = line.qty * qty / bom.quantity;
                explode(&line.item_code, scaled, price_list, db, level + 1, out).await?;
            }
        }
        _ => match item_price(db, item, price_list).await? {
            Some(rate) => out.cost += rate * qty,
            None => out.unset_bom_items.push(item.clone()),
        },
    }
    Ok(())
}
```

`MAX_LEVEL` is a named constant equal to 2 so the parity harness (§6) can prove equivalence with the Python. Do not "improve" it to unbounded recursion before the harness is green — that changes the numbers.

**Bug 3 — revenue definition.** Standardise on **`rounded_total`**, matching `ury_daily_p_and_l.py:297`, for three reasons: it is what the customer actually pays, it is what the printed invoice shows, and the round-off delta is separately posted to a ledger account so nothing is lost. ### 3.6 Concurrency — what upstream has, and what is missing

Upstream `sync_order` does a read-then-write compare-and-set on `last_modified_time`, plus `restrict_existing_order` on insert, plus `URY Table.occupied`, plus an `invoice_printed` flag. That is better than either prior plan credited — but it is still racy, because the check and the write are separate statements.

Three additions, all required before go-live:

```sql
-- 1. At most one open order per table, enforced by the database.
CREATE UNIQUE INDEX one_open_order_per_table
    ON pos_invoice (restaurant_table)
    WHERE docstatus = 0 AND restaurant_table IS NOT NULL;

-- 2. Idempotency: a replayed submit returns the original response
--    and, critically, the original invoice number.
CREATE TABLE idempotency_keys (
    key           UUID PRIMARY KEY,
    endpoint      TEXT        NOT NULL,
    invoice_name  TEXT,                    -- the number allocated on first attempt
    response      JSONB       NOT NULL,
    created_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

```rust
// 3. Row lock plus the retained compare-and-set, surfaced as a 409.
let current: PosInvoice = sqlx::query_as!(
    PosInvoice, "SELECT ... FROM pos_invoice WHERE name = $1 FOR UPDATE", name
).fetch_one(&mut *tx).await?;

if current.last_modified_time != client_seen_version {
    return Err(Error::Conflict {                      // → HTTP 409, client re-reads
        expected: client_seen_version,
        actual: current.last_modified_time,
    });
}
```

The idempotency key must be stored **with** the allocated invoice number. Otherwise a retried submit allocates a second number, which burns one from a legally gapless series (§5).

## 4. Architecture that fits Vercel honestly

### 4.1 What cannot run on Vercel, and the mechanism

| v1 proposed | Why it fails |
|---|---|
| Rust API on Vercel | No Rust runtime. Not a configuration problem. |
| `tokio::sync::broadcast` WebSocket fan-out | Functions are request-scoped. A broadcast sender reaches only subscribers on the one instance that happens to hold it. |
| `sqlx::Pool` | N cold instances × pool size exhausts Postgres `max_connections`. |
| `tokio::spawn` background tasks | The task dies when the function returns. |
| `"* * * * *"` KOT validation cron | Vercel cron is an HTTP trigger with plan-gated frequency; per-minute needs a paid plan and is still not a worker process. |
| Docker + Kubernetes, 3 replicas, PG primary+replica, Redis cluster | Not Vercel at all, and violates the owner's "simple architecture" constraint outright. |
| ESC/POS printing from a route handler | A Vercel function cannot open a TCP socket to `192.168.1.50:9100` on the restaurant LAN. |

### 4.2 The topology

```
[Vercel]        Next.js UI — marketing site + POS/manager screens
                Route handlers act as a thin BFF. They hold NO database
                connection; they forward to the API with a server-side key.
                    |
                    | HTTPS
                    v
[One box]       Rust API (Axum) + SSE realtime + the one cron
$5-10/mo        Fly.io 256MB, Railway, or Hetzner CX22
                Long-lived process, so ONE sqlx::Pool here is correct
                    |
                    +-- Postgres (Neon / Supabase / same box)
                    +-- Redis (Upstash, optional — only for menu/BOM cache)
                    |
                    | SSE / WebSocket over LAN
                    v
[Restaurant LAN] Print agent (Node or Rust)
                 Raw ESC/POS to :9100, local retry queue
                 THIS IS THE OFFLINE LIFELINE — kitchen keeps printing
                 through an ISP outage
```

Three moving parts, one of which is a small always-on box. That box is not optional in any design: realtime, printing, and cron all need it. v1's error was pretending otherwise while quietly specifying Kubernetes.

### 4.3 Stack, pinned

| Concern | Choice | Rationale |
|---|---|---|
| HTTP | `axum` 0.7 | Tower middleware composes; simpler mental model than Actix's actors for CRUD + realtime |
| DB | `sqlx` 0.8, Postgres | Compile-time SQL verification is the whole point for money queries. SeaORM's Active Record hides the joins that matter here |
| Decimal | `rust_decimal` 1.x | `NUMERIC` ↔ `Decimal`. Never `f64` |
| Realtime | `axum::response::Sse` | KOT updates are server→client only. SSE reconnects natively and traverses proxies that break WebSocket |
| Cron | `tokio-cron-scheduler` | Replaces the single `kotValidationThread` entry |
| Auth | `axum-extra` cookie + `argon2` | httpOnly session cookie beats a JWT in localStorage on a shared floor tablet |
| API types | `utoipa` → `openapi-typescript` | See §4.5 |

Note the honest framing: for one restaurant, neither Axum-vs-Actix nor SQLx-vs-SeaORM is a throughput decision. It is ergonomics and compile-time checking. v1's performance table was unmeasured, and the actual bottleneck was an N+1 (§3.2), which is a query bug, not a language problem.

### 4.4 Realtime

`grep publish_realtime` finds exactly one statically-named channel, `reload_ro`; the KOT channels are constructed dynamically per branch and production unit, so they do not appear as literals. Do not trust any list of channel names that was not read from the call sites.

SSE endpoints:

| Endpoint | Consumer | Payload |
|---|---|---|
| `GET /stream/kots?branch&production` | KDS, per station | KOT created / status changed |
| `GET /stream/tables?branch` | Floor view | occupied, merged, printed |
| `GET /stream/print?branch` | LAN print agent | print jobs |

KDS ticket lifecycle as an explicit state machine, since multiple cooks act on one ticket:

```
Pending → InProgress → Ready → Served
   └──────────────────────────→ Cancelled
```

Transitions are `PATCH /kots/:id/status` with the current state as a precondition, so two cooks tapping "start" simultaneously produce one transition and one 409, not two.

### 4.5 The contract problem

The Rust backend and the Vercel frontend are separate deployments with no shared types, so wire-format drift is silent — the backend adds a required field, the stale frontend 400s on every order.

Mitigation, pick one and enforce it in CI: annotate the Axum handlers with `utoipa`, emit `openapi.json` on build, and generate the TypeScript client with `openapi-typescript`. CI fails if the committed client differs from the generated one. That makes drift a build error instead of a dinner-service outage.

### 4.6 Offline is a Phase-0 data model constraint

Not a late feature. From day one:

- Every mutation carries a client-generated `Idempotency-Key` (§3.6).
- The client **never** invents an invoice number. Numbers are server-allocated (§5).
- Orders written offline queue in IndexedDB with a sync state, and replay by key.
- Conflict on the same table resolves via the 409 path in §3.6 — the client re-reads and re-presents, it does not blind-overwrite.

### 4.7 When the box dies mid-service

Single point of failure, so plan the degraded mode rather than pretending it away. The LAN print agent holds today's open tickets locally, so the kitchen can finish what is already cooking and reprint. The POS client queues new orders in IndexedDB. Nothing may allocate an invoice number while the box is down — those orders stay unbilled until it returns, then submit by idempotency key.

## 5. Money, tax, and the legally-binding parts

This section is the honest accounting of what v1 skipped entirely.

### 5.1 What ERPNext computes today

`ury_order.py` calls `calculate_taxes_and_totals()` at lines **637, 641, 1226, 1232**. Behind that one call:

| Behaviour | Rust rebuild cost |
|---|---|
| Sales Taxes and Charges template application | 1–2 wks |

| `net_total`, `total_taxes_and_charges`, `grand_total` | included above |
| `rounded_total`, `round_off`, `change_amount`, `write_off` | 0.5 wk |
| Item Price / Price List resolution | 1 wk |
| `is_pos=1` + `update_stock=1` → Stock Ledger with FIFO/moving-average | 3–4 wks |

| POS Invoice → consolidated Sales Invoice at day close | 1–2 wks |
| India Compliance: e-invoice IRN, e-way bill, GSTR-1/3B | 8+ wks |

That is on top of porting the 36 doctypes and 59 endpoints. It is the number both prior plans omitted, and it is why six reviewers said fork instead.

### 5.2 Indian GST, specifically

- **Restaurant service is generally 5% GST without ITC** for non-specified premises. This makes input-credit-style tax modelling wrong from the start — ERPNext's default POS template assumes ITC, so this is a week-1 configuration decision, not a code change.
- **CGST + SGST** intrastate, **IGST** interstate.
- **HSN/SAC on every line.** `ury_menu_item.json` has **no HSN field today** — this is a data backfill task that blocks go-live, not a schema afterthought.
- **Credit notes, not row deletes**, to reverse a submitted invoice.
- **E-invoice IRN** via the IRP once turnover crosses the threshold; QR on the invoice; 24-hour cancellation window.
- **GSTR-1/3B export.** ERPNext's India Compliance app provides e-invoice, e-way bill, and returns for free. A rewrite drops all of it.
- **Service charge must be opt-in**, not an auto-added line (CCPA 2022 guidelines).

### 5.3 Gapless invoice numbering — the mechanism

CGST Rule 46(b): consecutive series, unique per financial year, ≤16 characters, no gaps. The number must be allocated under a row lock inside the transaction, so a failed insert cannot burn one:

```rust
pub async fn allocate_invoice_number(
    tx: &mut Transaction<'_, Postgres>,
    series: &str,
    fiscal_year: &str,
    idempotency_key: Uuid,
) -> Result<InvoiceName> {
    // Replay returns the ORIGINAL number. Without this, a retried submit
    // allocates a second number and gaps the series.
    if let Some(existing) = sqlx::query_scalar!(
        "SELECT invoice_name FROM idempotency_keys WHERE key = $1", idempotency_key
    ).fetch_optional(&mut **tx).await?.flatten() {
        return Ok(InvoiceName(existing));
    }

    let next: i64 = sqlx::query_scalar!(
        r#"
        UPDATE naming_series
           SET next_number = next_number + 1
         WHERE series = $1 AND fiscal_year = $2
        RETURNING next_number - 1
        "#,
        series, fiscal_year
    )
    .fetch_one(&mut **tx)
    .await?;

    Ok(InvoiceName(format!("{series}-{fiscal_year}-{next:06}")))
}
```

A single `UPDATE … RETURNING` takes the row lock and increments atomically. If the surrounding transaction rolls back, the increment rolls back with it. A gap then only appears for a deliberately cancelled invoice, which must carry a logged void reason for the audit.

### 5.4 Money arithmetic rules

- `rust_decimal::Decimal` end to end; `NUMERIC(18,6)` in Postgres; **never `f64`**.
- **Serialise money as strings** on the wire. `PLAN.md` proposed `Number(...)` at the API boundary, which is IEEE-754 and corrupts paisa — the same bug the surrounding paragraph forbade.
- **Per-line GST computed before rounding**, so CGST and SGST each equal exactly half the total tax to the paisa.
- **Round-off applied once, at invoice level**, to the nearest rupee.
- **The round-off delta posts to a round-off ledger account** and appears on the P&L. It is not a display adjustment. Direction must be specified and tested.

### 5.5 Business day and timezone

Upstream already has the right primitive: `URY Report Settings.hours` as a cutoff, used by `ury_daily_p_and_l.py` via `TIMESTAMP(posting_date, posting_time)`. Formalise it:

- Business day is a half-open interval `[open, close)` in **Asia/Kolkata**, stored as `timestamptz`.
- A restaurant open 11:00–02:00 has a dinner shift crossing midnight; the 02:00 order belongs to the opening day.
- **India is UTC+05:30.** A naive datetime conversion during migration is wrong by half an hour, silently moving orders across the day boundary.

### 5.6 Cash and card

- **Z report** shows declared vs expected per payment mode, variance, and the cash deposit window. Cash above the daily threshold must be deposited by the next banking day (CGST Rule 56).
- **EDC terminals are not Razorpay.** Pine Labs / Paytm / Ingenico countertop terminals: POS sends the amount, cardholder enters PIN, terminal returns approval code and card last-4. Merchant onboarding is **2–4 weeks of bank lead time** and must start in parallel with development, not after. End-of-day batch settlement must reconcile to POS card totals **to the paisa** — a ₹1 delta means a missing transaction or a terminal-side void the POS never saw.
- Razorpay covers online UPI/card and its webhook is a legitimate Vercel serverless fit. It does not replace a countertop terminal.

## 6. Verification — the parity harness

The only credible way to validate a rewrite of money code is to run both implementations over the same data and diff.

```
Real POS Invoices (N days)
        │
        ├──→ Python/Frappe  ──→ net_total, tax, grand_total,
        │                        rounded_total, round_off, COGS
        │                                    │
        └──→ Rust           ──→ same fields ─┤
                                             ▼
                              assert equality to the paisa
```

**Gate: zero diffs across 30 consecutive days of real invoices**, including at least one month-end, one midnight-crossing dinner shift, one voided invoice, one split bill, and one merged-table bill. Thirty days because that is the shortest window that exercises a full GST return cycle.

Correctness gates, all runnable, all blocking:

| Gate | Assertion |
|---|---|
| GST arithmetic | 4×₹100, 5% GST, 10% discount → taxable 360, tax 18, total 378. Plus intrastate CGST+SGST split equal to the paisa, and an interstate IGST case |
| Gapless numbering | 100 concurrent submits produce 100 consecutive numbers, zero gaps, zero duplicates |
| Idempotency | The same key replayed 10× yields one invoice and one KOT |
| Midnight bucketing | A shift 22:00→02:00 buckets each invoice into exactly one business day (regression for bug 2) |
| Revenue definition | Shift-close total equals P&L total for the same day (regression for bugs 3 and 4) |
| KOT routing | A 3-station order produces 3 tickets with disjoint item sets (regression for bug 1) |
| COGS parity | Rust COGS equals Python COGS per item, including the `/ bom.quantity` normalisation and `Item Price` basis |
| Round-off | Residual lands in the round-off ledger; `round_off = rounded_total − grand_total` |
| Query budget | KOT generation for a 12-item, 3-station order issues ≤ 3 queries (regression for bugs 6 and 7) |

## 7. Roadmap — one developer, strangler-fig

Full rewrite before go-live is the highest-risk shape available. Sequence it so the system is shippable at every step and the money path moves **last**.

| Phase | Weeks | Work | Exit criteria |
|---|---|---|---|
| **0. Foundation** | 3 | Cargo workspace, Postgres schema for 12 root + 24 child tables, SQLx migrations, CI, `utoipa` → TS client generation | `cargo test` green; generated TS client committed and CI-checked |
| **1. Read-only mirror** | 4 | Rust serves reads only: menu resolution, table state, KOT display. Frappe still owns all writes | Vercel UI reads from Rust; byte-identical payloads vs Frappe for the same queries |
| **2. KOT path** | 4 | Move KOT generation and routing to Rust behind a flag. Lowest money exposure — this is why it goes first | KOT routing gate green; query budget gate green; flag flippable both ways |
| **3. Print agent** | 3 | LAN agent: ESC/POS to :9100, 58/80mm column math, Devanagari via `GS v0` raster, cut/drawer commands, local retry queue, print job log for reprint audit | Kitchen prints correctly through a simulated 10-minute ISP outage |
| **4. Order writes** | 5 | `sync_order`, merge, split, transfer. Idempotency keys, row locks, unique open-order index. Still no money | Concurrency gates green; 409 path exercised by two simulated waiters |
| **5. Money layer** | 10–14 | Tax engine, rounding, gapless numbering, shift close, COGS. **Parity harness runs continuously from day one of this phase** | 30 consecutive days of zero money diffs |
| **6. Migration + cutover** | 4 | Name→ID maps, child-table FKs, `docstatus` → enum, CSV → join table, naive datetime → `timestamptz` at UTC+05:30, `Data`-typed numerics validated, revenue and closing stock reconciled to the paisa | Dry-run migration reconciles; rollback rehearsed |
| **7. Stabilise** | 3 | Load test, degraded-mode drills, runbook | Single-box failure drill passes |
| **Total** | **36–40 weeks** | one developer | |

Running in parallel from week 1: **EDC merchant onboarding** (2–4 weeks of bank lead time — start it early, it is not on the critical path but it blocks go-live if left late).

Note the total: **36–40 weeks solo**, against v1's claim of 24–32 weeks (which assumed 3–4 developers). And this figure *still* accepts the losses in §8.

### The parity harness was adversarially validated

A harness that cannot fail proves nothing. I injected v1's exact COGS defect into the Python oracle — deleted the `/ bom["quantity"]` normalisation at `scripts/parity_reference.py:231` — and confirmed the harness catches it:


### Findings from the build that amend this plan

**Menu pricing — §3.3 was wrong.** This plan stated menu prices resolve from ERPNext `Item Price` on the selling price list. The source says otherwise: price comes from **`ury_menu_item.rate`**, a `Currency` field on the child table (`ury_pos/api.py:79,87`; `ury_menu_item.json:34`). `Item Price` is used only in the aggregator flow (`api.py:829`). The *buying* price list remains correct for COGS (§3.4) — those are two separate bases, and conflating them was the error.

**Menu validity — no date window exists.** `ury_menu.json` has exactly one gating field, `enabled` (Check, default 1, line 21). There are no `valid_from`/`valid_to` fields, so the `at: DateTime<Utc>` parameter in `resolve_menu` is currently unused and retained only for future-proofing.

**Menu precedence is conditional, not a simple cascade.** Room-wise applies only when `URY Restaurant.room_wise_menu = 1` (`api.py:40-44`); order-type-wise additionally requires the cashier role (`api.py:50-60`). Both fall through to `active_menu` when no mapping exists (`api.py:46,62`), and only a missing default raises (`api.py:71-72`).

**One upstream guard could not be ported.** `unmerge_tables` has a "cannot unmerge active tables" check (`ury_order.py:469`) that needs open-invoice lookups including a `custom_merged_tables LIKE` scan (`:441`). `OrderRepo::count_separate_active` is not a substitute — it counts unprinted drafts per table and misses invoices that reference a member only through `custom_merged_tables`. Enforcing it requires adding `has_open_invoices()` to the port.

**The KOT query budget has a floor of 3 + one probe per emitted ticket.** The `New Order` → `Order Modified` flip is defined per invoice *and* production unit (`ury_kot_generate.py:159`), and `KotRepo` exposes no batched form. Batched fetches are 3 flat regardless of item count; the EXISTS probes scale with stations that actually receive items. Stations receiving nothing are never probed.

**Two upstream `frappe.throw` sites have no matching error variant** and were made degenerate no-ops rather than misfiled onto unrelated kinds: "Select at least one table to merge" (`ury_order.py:39`) and "Table is not merged" (`:463`).

### Not built — and why

| Remaining | Blocker |
|---|---|
| SQL adapter implementing every trait in `ports.rs` | No PostgreSQL on this machine. Every port is currently a trait with zero implementations, so nothing persists |
| HTTP layer — 59 endpoints, SSE realtime | Depends on the SQL adapter |
| LAN print agent — ESC/POS, `GS v0` raster for Indic text | Needs real printer hardware to verify |
| 30-day real-invoice replay (§6 cutover gate) | Needs a live Frappe instance and production data |
| Data migration (§7 Phase 6) | Needs both databases |

What exists is the **domain layer**: pure logic with storage behind traits, which is why all 132 tests run with no database. That is Phase 1 of §7 done properly, and it is useful either way — if you fork URY, these are the corrected algorithms to port back into Python; if you continue in Rust, it is the foundation the adapter plugs into.

This document is what a competent execution of the Rust path looks like. It is now internally honest: real schema, real signatures, real arithmetic, a deployment story that matches Vercel's actual constraints, and a cost that includes the money layer.

If the goal is a running restaurant, fork. If the goal is owning the stack end to end with eyes open about the price, this plan is executable — and §7's kill criteria tell you when to stop.
